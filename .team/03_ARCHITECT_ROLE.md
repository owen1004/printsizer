# Architect 角色 SOP - 架構師

> **職責**：確保整體方向、識別風險、把關大改動

---

## 何時觸發 Architect 角色？

✅ **必須觸發**
1. PM 階段完成後（@ARCHITECT_REVIEW）
2. 需要改變設計方向時（@ARCHITECT_INTERVENTION）
3. 風險評估與把關

✅ **防線機制**
- 中途發現「可能偏離大方向」的修改 → 立即觸發

## Architect 工作流程

```
【輸入】
PM 需求分析報告 + 用戶確認
  ↓
【Architect 分析階段】
  ├─ 架構設計（模組劃分、數據流）
  ├─ 可行性評估（SDK 支援度、技術棧）
  ├─ 風險識別（潛在問題、依賴關係）
  ├─ 🆕 測試策略規劃 ← 新增
  │  ├─ C++ 外掛 → TestLab（自動化）
  │  └─ .jsx 腳本 → 三層測試（自動化 + 手動）
  └─ 決策記錄（為什麼這樣設計？）
  ↓
【Architect 審核階段】
  ├─ 評估是否偏離原方向
  ├─ 是否引入技術債
  └─ 何時償還技術債
  ↓
【輸出】
Architect 審核報告 → 用戶確認 ✓
```

## 🆕 測試架構設計指南（Architect 角色）

### 何時需要規劃測試架構？

✅ **必須規劃**：
- 開發任何可測試的邏輯模組（.jsx 或 C++）
- 估算工作時間時需考慮測試時間（測試佔 20-30%）

### 測試架構設計決策

#### 決策 1：選擇適當的測試方式

```
┌─ 開發什麼？
│
├─ C++ 編譯外掛
│  └─ 使用 TestLab（自動化單元 + 集成測試）
│     + 人工測試（UI/相容性驗證）
│
├─ .jsx 腳本 / UXP 邏輯
│  └─ 使用三層測試系統
│     ├─ Layer 1：單元測試（test_template_unit.jsx）
│     ├─ Layer 2：集成測試（test_template_integration.jsx）
│     └─ Layer 3：UI 手動測試（UI_Test_Checklist.md）
│
└─ 純 UI/互動元件
   └─ 只需手動測試（無自動化測試）
```

#### 決策 2：模組應該「可測試」

```
設計原則：
┌─────────────────────────────────┐
│ 核心邏輯層（可測試）             │
│ ├─ KnifelineGenerator.jsx        │
│ ├─ Validation.jsx               │
│ └─ Logger.jsx                   │
└─────────────────────────────────┘
           ↓ 依賴
┌─────────────────────────────────┐
│ Illustrator DOM 層（難以測試）   │
│ ├─ 選取物件操作                  │
│ ├─ 生成路徑/群組                │
│ └─ 更新文檔                      │
└─────────────────────────────────┘

✅ 最佳做法：
- 將「計算邏輯」與「DOM 操作」分開
- 邏輯層用自動化測試驗證
- DOM 層用手動測試驗證
```

#### 決策 3：時間估算要包含測試

```
新功能估算方式（以「刀模線工具」為例）

不含測試：
├─ 需求分析：1 天
├─ 架構設計：1 天
├─ 代碼開發：3 天
└─ 小計：5 天

✅ 包含測試（推薦）：
├─ 需求分析：1 天
├─ 架構設計：1 天
├─ 代碼開發：2 天  ← 減少（因為有測試自動化）
├─ 自動化測試編寫：1 天  ← 新增
├─ 手動 UI 測試：0.5 天  ← 新增（比之前快）
└─ 小計：5.5 天  ← 總時間反而接近

效果：
- 代碼質量 ↑↑↑（邏輯層 100% 驗證）
- 開發效率 ↑（手動測試時間節省 50-67%）
- 維護成本 ↓（發現 bug 時自動化測試能快速定位）
```

## 🆕 技術債管理 - Architect 的責任

> **定義**：技術債 = 快速實現卻質量不完美的代碼/設計，需要後續償還

### Architect 在技術債中的角色

Architect 是整個項目的**技術債把關者**，負責：
1. 識別何處**可以接受技術債**，何處**不能**
2. 為接受的技術債制定**償還計畫**
3. 在開發過程中**監控技術債累積**
4. 記錄所有決策供未來參考

### 技術債的分類

#### ✅ 可以接受的技術債

```
場景：為了趕時間，短期內可以接受不完美的實現

範例：
- 「先用快速排版算法（正確率 95%），後續優化到 99%」
- 「先用簡單的暴力算法，後續優化複雜度」
- 「先支援 3 種物件類型，後續擴展到 10 種」
- 「先手動測試，後續編寫自動化測試」

條件（必須同時滿足）：
✅ 必須有明確的「償還計畫」（什麼時候修復？誰負責？）
✅ 必須記錄「為什麼接受」（商業理由、時間壓力等）
✅ 必須記錄「影響範圍」（哪些功能可能受影響？）
✅ 必須不影響「核心邏輯」（關鍵部分必須做對）
✅ 必須「易於償還」（改動隔離，不與其他代碼耦合）
```

**記錄格式**：
```markdown
【技術債決策 #1】

描述：先用快速排版算法
現狀：正確率 95%，性能好
計畫償還：Sprint 3
償還方式：優化算法至 99% 正確率
負責人：Developer A
風險：邊界情況（特殊形狀、超大物件）可能排版不完美
```

#### ❌ 不能接受的技術債

```
場景：不管時間多緊張，也不能跳過

❌ 不能接受的技術債：

1. 「跳過錯誤處理」
   原因：無法預測的 crash，用戶會遇到
   
2. 「跳過邊界條件檢查」
   原因：會導致數據損壞、邏輯錯誤
   
3. 「使用過時/不安全的技術」
   原因：後期 bug 多，維護成本高
   
4. 「完全無文檔無註釋」
   原因：後期無法維護，知識流失
   
5. 「核心模組設計不清楚」
   原因：影響所有相關功能，後期改動困難

規則：「核心邏輯必須做對，邊界優化可以延後」
```

### 技術債的識別與評估

#### 在架構設計階段

**Architect 應該提出的問題**：
- [ ] 這個模組有無**過度簡化**？（留有未來擴展空間？）
- [ ] 這個設計有無**隱藏假設**？（邊界條件都考慮了？）
- [ ] 這個實現有無**可能的優化空間**？（現在做最優，還是先快速？）
- [ ] 有無**依賴外部庫**的風險？（庫是否穩定？許可協議？）

**應該記錄的技術債**：
```markdown
【識別於架構設計階段】

模組：座標轉換層
可能的技術債：
- 精度問題：目前用浮點數，極端情況下可能有精度誤差
  └─ 是否需要改成定點數？評估：改動大，暫不做
- 性能優化：目前每次轉換都重新計算，可以快取
  └─ 優先級：P1，Sprint 2 優化
```

#### 在開發中監控

**Architect 應該定期檢查**：
- [ ] Developer 是否在「不應該有技術債的地方」引入了技術債？
- [ ] 已接受的技術債是否被「誤解」了？
- [ ] 有無新的技術債風險出現？

### 技術債償還計畫

#### 1️⃣ 記錄格式

在 `DECISIONS.md` 中記錄：

```markdown
【技術債 #1】座標精度問題

現狀：
- 使用浮點數進行座標計算
- 在特殊情況下（極端尺寸、複雜形狀）可能有 1-2px 誤差
- 影響：≤ 0.1% 的用戶受影響

為什麼接受：
- 改用定點數需要重寫座標層（5 天工作量）
- 現在 95% 的使用情況沒有問題
- 商業優先級：先上線，後優化

償還計畫：
- 時機：Sprint 3（2026-05-01）
- 工作量：5 天
- 負責人：Developer B
- 驗收標準：精度提升至 ±0.1px，所有測試通過

風險：
- 改動涉及座標層，需要充分測試
- 可能影響性能（需要基準測試對比）

決策者：Architect A
簽署日期：2026-04-20
```

#### 2️⃣ 償還優先級

```
🔴 P0 - 必須立即償還（下個 Sprint）
- 影響核心功能的技術債
- 已有多個用戶反饋的技術債
- 安全/穩定性相關的技術債

🟡 P1 - 應該在 2-3 個 Sprint 內償還
- 影響性能/易用性的技術債
- 維護成本較高的技術債

🟢 P2 - 可以延後償還（後續計畫）
- 影響範圍小的技術債
- 優化性質的技術債
```

#### 3️⃣ 監控和追蹤

**🆕 跨 Sprint 技術債責任追蹤**：

| 責任角色 | 檢查時機 | 檢查項目 | 行動 |
|----------|--------|--------|------|
| **Architect** | Sprint 計畫會議 | 待償還技術債清單是否還有效 | 若計畫變更，更新 DECISIONS.md |
| **Architect** | Sprint 開始時 | 本 Sprint 要償還哪些？缺人力嗎？ | 與 PM 溝通優先級調整 |
| **Developer** | 代碼實現期間 | 新發現的技術債是否及時記錄 | 記錄在 Commit 訊息或清單 |
| **Architect** | Sprint 中期（若需要） | 償還進度是否正常 | 若滯後，調整計畫 |
| **Architect** | Sprint 回顧會議 | 償還進度驗收 | 已完成？延期？新發現？ |
| **QA** | 測試階段 | 已接受的技術債是否在可接受範圍內 | 紀錄驗證結果 |

**建議的做法**：

```
【每個 Sprint 開始】
Architect 檢查：
- 有多少個技術債待償還？
- 上個 Sprint 的技術債償還情況如何？
- 這個 Sprint 要償還哪些？（P0 優先）
- 有無新的技術債出現？
- 是否有技術債計畫被推遲？（查看 DECISIONS.md）

【Sprint 中期檢查（若技術債 > 5 項）】
Architect 與 Developer 同步：
- 償還進度是否按計畫進行？
- 是否遇到阻礙？
- 是否需要調整優先級？

【Sprint 回顧】
Architect 領導討論：
- 這個 Sprint 償還了哪些技術債？✅
- 推遲償還的原因是什麼？
- 是否有新的技術債被發現？
- 下個 Sprint 的償還計畫是什麼？
- 健康指標是否達到？（🟢/🟡/🔴）
```

**跨 Sprint 技術債狀態追蹤**（記錄在 DECISIONS.md）：
```markdown
【技術債 #X】座標精度優化

決策日期：2026-04-20
當前狀態：待償還
計畫償還 Sprint：Sprint 3

== Sprint 1 回顧（實際情況）==
- 計畫：償還
- 實際：延期原因：需要設計更多測試用例
- 新計畫：Sprint 2 開始

== Sprint 2 回顧（實際情況）==
- 計畫：償還
- 實際：進行中 (70%)
- 預計完成：Sprint 2 結束

== Sprint 3 回顧（實際情況）==
- 計畫：完成驗收
- 實際：✅ 完成，QA 驗收通過
```

### 防止技術債螺旋

#### ⚠️ 警示跡象

如果出現以下情況，說明技術債已經失控：

```
❌ 跡象 1：「每個 Sprint 都在償還舊技術債」
   原因：新的技術債累積速度 > 償還速度
   解決：暫停新功能，集中償還 2-3 個 Sprint

❌ 跡象 2：「開發速度越來越慢」
   原因：技術債導致代碼複雜度上升，改動困難
   解決：優先償還影響開發效率的技術債

❌ 跡象 3：「Bug 率上升」
   原因：技術債導致代碼質量下降
   解決：識別根本技術債，計劃性償還

❌ 跡象 4：「新 Developer 適應困難」
   原因：代碼質量差，難以理解
   解決：優先改進代碼可讀性和文檔
```

#### ✅ 健康指標

```
✅ 健康狀態：
- 每個 Sprint 償還的技術債 ≥ 新增技術債
- 技術債清單保持在 5-10 項以內
- P0 技術債在 2 週內償還
- 開發速度保持穩定或上升
- Bug 率保持在預期範圍內
```

## 🆕 版本回滾主動提醒機制（G-05）

> Architect 是系統的「店長」，負責**主動偵測**回滾需求並提醒用戶，由用戶最終拍板。

### 觸發條件：Architect 何時主動提醒？

```
以下任一情況發生，Architect 必須主動介入：

🔴 立即提醒：
  1. QA 發現「已通過測試的功能出現回歸（regression）」
  2. 部署後用戶回報「新版本比舊版本更差」
  3. DevOps 部署失敗，無法前進

🟡 評估後提醒：
  4. 新代碼導致性能下降 > 20%
  5. 新版本引入的 Bug 數量 > 修復的 Bug 數量
```

### 回滾決策流程

Architect 偵測到觸發條件後，**主動向用戶報告**，格式如下：

```
Architect 提醒：

⚠️ 偵測到【問題類型】，建議評估是否回滾。

【問題摘要】
- 發現時間：[時間]
- 影響範圍：[功能 / 模組]
- 嚴重程度：P0 / P1

【選項供您決策】

選項 A：立即回滾到 [vX.X.X]
  ├─ 優點：最快恢復穩定（預計 < 15 分鐘）
  ├─ 缺點：[本次改動的好處] 將暫時消失
  └─ 適合：P0 崩潰、大範圍功能失效

選項 B：緊急 Hotfix（不回滾）
  ├─ 優點：保留本次改動的其他功能
  ├─ 缺點：修復時間較長（預計 30-60 分鐘）
  └─ 適合：問題局限在單一函數，原因明確

選項 C：暫時限制使用範圍（Feature Flag）
  ├─ 優點：對部分用戶隱藏問題功能，主流程不受影響
  ├─ 缺點：需要額外代碼改動
  └─ 適合：只有特定條件才會觸發的問題

【Architect 建議】：[建議選項 X，理由：...]

請您決定，我會立即執行。
```

### 回滾授權規則（無需等待用戶的情況）

| 情況 | 授權 | 說明 |
|------|------|------|
| P0：應用崩潰 100% 必現 | DevOps 可自行回滾，同時通知用戶 | 不等決策，先救災 |
| P1：核心功能失效 | 需用戶確認後由 DevOps 執行 | Architect 提供選項，用戶 5 分鐘內決策 |
| P2：局部問題 | 需 Architect + 用戶雙確認 | 走正常決策流程 |

## Architect 提示（最佳實踐）

1. **識別風險，不要假設**
   - 列出所有可能失敗點
   
2. **決策必須可解釋**
   - 為什麼選擇 X 而不是 Y？
   
3. **留意技術債**
   - 必要時可接受技術債，但要有償還計畫
   
4. **與用戶對齐方向**
   - 大改動需獲批准

# 問題定義標準化流程

> **核心目的**：建立清晰、結構化的問題描述規範，確保「問題定義 → Claude 理解 → 執行修改」三步達到 100% 認知一致，防止因誤解導致的開發返工

**最後更新**：2026-04-11  
**相關文檔**：[Translator 澄清機制](08_TRANSLATOR_ROLE.md)、[修改管理流程](10_CHANGE_MANAGEMENT_PROCESS.md)

---

## I. 背景與事故回顧

### 歷史教訓（真實案例）
某次 Illustrator 智能排版工具開發中，出現以下問題鏈：

```
【問題描述】用戶：「座標系統有問題」
                      ↓
【理解偏差】Claude：假設是「座標轉換邏輯錯誤」
                      ↓
【倉促執行】直接修改代碼，未做備份、未確認理解
                      ↓
【測試失敗】修改後測試仍失敗，用戶澄清：「實際是容器邊界計算」
                      ↓
【返工成本】整個專案需要重新開始
            消耗：8+ 小時、數千 token、高額重做成本
```

### 根本原因分析
| 環節 | 問題 | 後果 |
|------|------|------|
| **問題描述** | 「座標有問題」太籠統 | Claude 無法精準定位根因 |
| **理解確認** | Claude 未反問具體症狀 | 基於猜測開始修改 |
| **修改計畫** | 未做備份/回滾規劃 | 錯誤修改無法恢復 |
| **認知一致性** | 只有 30% 的信心執行 | 盲目修改，浪費資源 |

## II. 問題定義的 5 個必填項

在向 Claude 提交問題前，**必須**包含以下 5 項資訊：

### 1️⃣ **問題陳述（Problem Statement）**
- **定義**：用 1-2 句話簡述「現象」和「期望」的差距
- **格式**：
  ```
  【現象】：當我 [執行操作]，結果 [發生了什麼]
  【期望】：應該 [預期行為]
  【影響】：導致 [什麼後果]
  ```

**✅ 好的例子**：
```
【現象】：排版超過 5 個物件時，容器邊界計算錯誤，導致物件被切掉
【期望】：無論物件數量多少，都應該自動縮放至容器邊界內
【影響】：Critical - 無法使用大規模拼版功能
```

❌ **不好的例子**：
```
「座標有問題」
「排版不行」
```

---

### 2️⃣ **複現步驟（Reproduction Steps）**
- **定義**：逐步列出如何觸發問題的確切操作
- **格式**：按順序編號，每步一句

**✅ 好的例子**：
```
1. 打開測試檔案「layout_test_5objects.ai」
2. 進入 Cut Pro 外掛
3. 點擊「智能拼版」按鈕
4. 選擇 5 個物件 (每個約 200mm × 100mm)
5. 拖曳至容器 (300mm × 300mm)
6. 點擊「自動排列」
→ 觀察到：右側物件超出邊界，被意外切掉
```

❌ **不好的例子**：
```
「創建幾個物件然後拼版就壞了」
```

---

### 3️⃣ **預期 vs 實際（Expected vs Actual）**
- **定義**：用對比表清晰展示差距

**✅ 好的例子**：
| 場景 | 預期結果 | 實際結果 | 差距 |
|------|---------|---------|------|
| 5 個物件排列 | 全部自動縮放至容器內 | 右側物件超出容器 | 邊界計算缺漏 20% 面積 |
| 旋轉 90° 後排列 | 邊界應重新計算 | 仍按原始尺寸計算 | 旋轉後未更新邊界 |

---

### 4️⃣ **上下文信息（Context）**
- **定義**：提供足夠的環境信息，幫助 Claude 理解約束

**包含內容**：
- 📦 使用的文件（檔名、大小、特性）
- 🎨 Illustrator 版本（2021/2023/2026）
- 🔧 外掛版本 / 相關模組版本
- 📐 涉及的 API 或算法（如果已知）
- ⚙️ 設定值或參數

**✅ 好的例子**：
```
【使用環境】
- 檔案：layout_test_5objects.ai (來自 /test-data/ai-files/)
- Illustrator 版本：2026 (build 2026.1)
- 外掛版本：Cut_Pro v2.1.0
- 測試數據：5 個矩形物件，尺寸 200×100mm
- 容器：300×300mm 文本框

【相關代碼】
- src/algorithms/nesting.jsx (第 145-180 行 - 邊界計算)
- src/utils/bounds.jsx (getBounds 函數)
```

---

### 5️⃣ **重要性與緊急度（Priority & Risk）**
- **定義**：評估此問題的業務影響

**優先級分類**：

| 級別 | 定義 | 例子 |
|------|------|------|
| **P0 / Critical** | 功能完全無法使用、數據損失風險 | 應用崩潰、大量物件丟失 |
| **P1 / Major** | 主功能受阻、影響核心流程 | 排版超過 5 個物件失敗 |
| **P2 / Minor** | 次要功能缺陷、可繞過 | 旋轉後邊界計算不精確（+/- 5mm） |
| **P3 / Trivial** | 外觀/性能微調 | UI 字體大小差 2px |

**風險評估**：
- 🔴 **High Risk**：可能波及其他模組 / 需要更改數據結構
- 🟡 **Medium Risk**：局部修改 / 需要新增測試
- 🟢 **Low Risk**：獨立函數修改 / 有現成測試覆蓋

### A. Bug 報告
```markdown

### 1. 問題陳述
【現象】...
【期望】...
【影響】...

### 2. 複現步驟
1. ...
2. ...
3. ...

### 3. 預期 vs 實際
| 場景 | 預期 | 實際 |
|------|------|------|
| ... | ... | ... |

### 4. 上下文
- 檔案：...
- 版本：...
- 相關代碼：...

### 5. 優先級
- **優先度**：P[0-3]
- **風險等級**：High / Medium / Low
- **影響範圍**：[已知受影響的功能模組]
```

### B. 功能需求
```markdown
## ✨ Feature: [功能名稱]

### 1. 需求陳述
【背景】為什麼需要這個功能？
【目標】期望達成什麼效果？
【使用場景】在什麼情況下用戶會需要它？

### 2. 接受標準（AC：Acceptance Criteria）
- [ ] 能處理 [邊界情況 1]
- [ ] 性能指標：[預期速度]
- [ ] 兼容性：[支援版本]

### 3. 上下文
- 相關功能模組：...
- 依賴工具/庫：...
- 預計影響範圍：...

### 4. 優先級
- **優先度**：P[0-3]
- **目標 Sprint**：...
- **估計工作量**：[快速判斷]
```

### C. 設計/架構問題
```markdown
## 🏗️ Architecture: [變更題目]

### 1. 當前狀態
【現狀】現在如何實現的？
【瓶頸】有什麼問題？
【成本】保持現狀的代價是什麼？

### 2. 提案
【方案】建議如何改進？
【優勢】相比現狀的好處？
【代價】實施成本有多高？

### 3. 影響評估
- 影響文件：[列表]
- 影響功能：[列表]
- 破壞性變更：Yes / No

### 4. 優先級
- **優先度**：P[0-3]
- **複雜度**：Low / Medium / High
```

## IV. 提交流程（3 步）

### Step 1: 自檢清單（提交前自行檢查）

在提交問題給 Claude 前，**必須確認所有項目**：

```
🔍 自檢清單

【問題陳述】
☑ 用 1-2 句話簡述現象和期望的差距？
☑ 說明了影響？

【複現步驟】
☑ 列出了逐步操作指令（至少 3 步）？
☑ 步驟足夠詳細，他人能復現？

【預期 vs 實際】
☑ 清晰展示了預期和實際的差距？
☑ 用量化指標（尺寸、時間、數量）說明差距？

【上下文】
☑ 提供了檔案名、版本號、環境信息？
☑ 標註了相關代碼位置（檔案 + 行號）？

【優先級】
☑ 評估了 P0-P3 的優先度？
☑ 評估了 High/Medium/Low 的風險？

✅ 全部確認後，才能提交給 Claude
```

### Step 2: 提交給 Claude（含澄清流程）

提交時，使用以下格式：

```markdown
## 問題提交

[複製上面的完整模板內容]

---
**額外信息**（如果有）：
- 已嘗試的解決方案：...
- 相關的 GitHub Issues：...
- 歷史背景：...
```

**Claude 的 Translator 角色將**：
1. ✅ 掃描是否有遺漏的信息
2. ❓ 如果有缺漏，提出澄清問題（參考 [08_TRANSLATOR_ROLE.md](08_TRANSLATOR_ROLE.md) 的「強制澄清機制」）
3. 📋 與用戶確認完整理解後，標記「認知一致 ✅」
4. 🔧 開始執行修改

### Step 3: 執行與驗證

一旦「認知一致 ✅」，進入 [修改管理流程](10_CHANGE_MANAGEMENT_PROCESS.md)：
- 制定備份與回滾計畫
- 執行修改
- 進行驗證測試

## V. 常見誤區與改進

### ❌ 誤區 1: 過於籠統的問題描述

**常見形式**：
```
「排版有問題」
「座標系統不對」
「性能太慢」
```

**改進方法**：加入「現象 + 期望 + 具體數字」
```
✅ 「排版 5 個物件時，右側物件超出容器邊界（實際 350mm，容器限制 300mm），
    預期應自動縮放，影響拼版功能完全無法使用（P0）」
```

---

### ❌ 誤區 2: 缺少複現步驟

**常見形式**：
```
「有時候會出現這個問題」
「在某些檔案裡會崩潰」
```

**改進方法**：提供確定性的複現路徑
```
✅ 1. 打開 /test-data/large_objects.ai
   2. 選擇前 5 個物件
   3. 點擊「智能拼版」
   4. 容器設為 300×300mm
   → 問題必現
```

---

### ❌ 誤區 3: 沒有上下文信息

**常見形式**：
```
「不知道什麼版本」
「沒看過代碼」
```

**改進方法**：記錄環境與代碼位置
```
✅ 【環境】
   - Illustrator 2026.1
   - Cut_Pro v2.1.0
   - 檔案：layout_test_5objects.ai
   
   【相關代碼】
   - src/algorithms/nesting.jsx (第 145-180 行)
   - src/utils/bounds.jsx (getBounds 函數)
```

---

### ❌ 誤區 4: 沒有優先級評估

**常見形式**：
```
「很重要」
「急」
```

**改進方法**：用標準優先級框架
```
✅ 【優先度】P1 (Major)
   【風險等級】Medium Risk (需修改邊界計算邏輯，涉及多個模組)
   【影響範圍】排版功能核心流程
```

## VIII. 常見問題（FAQ）

### Q1: 「我只知道有問題，不知道怎麼複現」怎麼辦？

**A**：這是常見情況。建議：
1. **主動測試**：嘗試不同的檔案、設定、操作順序
2. **記錄細節**：每次失敗時記下當時的操作步驟
3. **尋找規律**：找出 100% 必現的條件（如「只有超過 5 個物件時」）
4. **提交初稿**：即使不完全，也可先提交「已測試場景」+ 「可能相關因素」，由 Claude 協助診斷

提交時標註：
```
【已知信息】
- 條件 A 時必現
- 條件 B 時不現

【未知】
- 與 [具體參數] 的關係

【建議】
- Claude 可協助設計測試場景
```

---

### Q2: 「優先級怎麼判斷」？

**A**：用以下三維評估法：

```
優先度 = (業務影響) × (用戶頻率) × (修復難度反比)

【業務影響】
- P0：功能完全不可用 / 數據丟失
- P1：主功能受阻
- P2：次功能缺陷
- P3：微調

【用戶頻率】
- 高：天天遇到
- 中：每周遇到
- 低：罕見情況

【修復難度】
- 低難度修復 + 高頻率 + 高影響 = 優先
- 高難度修復 + 低頻率 + 低影響 = 延後
```

---

### Q3: 「如果我提交了不完整的問題怎麼辦」？

**A**：Translator 角色會：
1. 🚩 指出缺漏的信息
2. ❓ 提出澄清問題（最多 5-7 個）
3. 👤 等待用戶補充完整
4. ✅ 確認認知一致後再執行

**這是流程的一部分，不是失敗。** 提前澄清比倉促修改然後返工便宜得多。

## IX. 最佳實踐建議

### 📝 建議 1：建立「問題日誌」

在項目進行中，隨時記錄遇到的問題（不必立即提交）：

```
【2026-04-11 14:30】排版超過 5 個物件時邊界計算錯誤
  - 複現：large_objects.ai + 5 物件 + 300mm 容器
  - 現象：右側物件超出 50mm
  - 根因：[待確認]

【2026-04-11 15:00】旋轉 90° 後邊界未更新
  - 複現：正方形物件→旋轉→重新排版
  - 現象：仍按原始尺寸排列，導致重疊
```

累積到足夠信息時，再整理成正式問題提交。

---

### 📝 建議 2：截圖 + 標註

對於視覺問題，提交截圖並標註：

```
【截圖內容】

- 標註尺寸、數字（如「實際 350mm / 預期 300mm」）
- 顯示前後對比（修改前 → 修改後）
```

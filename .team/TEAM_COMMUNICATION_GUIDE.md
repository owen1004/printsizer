## 📋 角色間的依賴關係圖

```
【初始】
  ↓
【PM】需求和產品策略分析
  ├─ 輸出：產品規劃報告 + 需求澄清報告
  ├─ 簽署：用戶確認 ✓
  └─ 下一步：Architect 審核
  ↓
【Architect】架構設計和風險評估
  ├─ 輸入：PM 報告
  ├─ 輸出：架構審核報告 + 技術方案
  ├─ 簽署：Architect 決策 ✓
  └─ 下一步：UI&UX 設計
  ↓
【UI&UX 設計師】用戶體驗設計
  ├─ 輸入：Architect 報告 + 技術方案
  ├─ 輸出：用戶旅程 + UI 原型 + 設計規範
  ├─ 簽署：Architect & Developer 確認可實現 ✓
  └─ 下一步：開發實作
  ↓
【Developer（開發）】代碼實現
  ├─ 輸入：UI&UX 設計規範 + Architect 技術方案
  ├─ 輸出：Code Commit（含語義化訊息）
  ├─ 簽署：Code Review 通過 ✓
  └─ 下一步：QA 測試
  ↓
【QA】品質驗證
  ├─ 輸入：Developer 代碼
  ├─ 輸出：自動化測試報告 + 手動測試報告
  ├─ 決策：通過 / 退回（Bug 清單）
  └─ 下一步：DevOps 或 Bug Fix
  ↓
【DevOps】版本發佈
  ├─ 輸入：QA 通過確認
  ├─ 輸出：部署完成 + 版本號更新 + git tag
  ├─ 簽署：部署驗證 ✓
  └─ 下一步：Doc Manager
  ↓
【Doc Manager】文檔同步
  ├─ 輸入：DevOps 部署完成 + 版本信息
  ├─ 輸出：所有文檔更新 + 版本號對齊
  ├─ 簽署：文檔完整性確認 ✓
  └─ 下一步：發佈完成
  ↓
【Translator】持續監聽
  ├─ 自動監聽：用戶輸入是否符合 @CODE 格式
  ├─ 轉化：非標準輸入 → 標準指令
  └─ 行動：轉化完成 → 調用對應角色
```

## 🗣️ 各角色的溝通責任

### 1️⃣ PM 的溝通

**與 Architect 的溝通**
- **何時**：PM 分析完成後，向 Architect 提交報告
- **溝通內容**：
  - ✅ 需求澄清報告（功能清單、優先級、工作量估算）
  - ✅ 資料庫檢索結果（現成代碼推薦）
  - ✅ 產品規劃報告（JTBD、Persona、競品分析、願景）
- **期望反饋**：Architect 是否同意技術方案？有無架構風險？

**與用戶的溝通**
- **何時**：產品規劃和需求澄清完成後
- **溝通方式**：正式的「產品規劃報告 + 需求澄清報告」簽署
- **確認內容**：
  - 產品方向是否正確？
  - MVP 範圍是否清晰？
  - 優先級排序是否同意？

**防線機制**
- ⚠️ 如發現產品方向偏離 → 立即觸發 @PM_INTERVENTION → 與用戶重新評估

---

### 2️⃣ Architect 的溝通

**與 PM 的溝通**
- **何時**：收到 PM 報告後
- **溝通內容**：
  - 架構是否可行？
  - 技術方案評估
  - 風險識別和緩解方案
  - 與既有模組的影響評估

**與 UI&UX 的溝通**
- **何時**：架構設計完成後，向 UI&UX 設計師移交
- **溝通內容**：
  - ✅ 架構設計圖（模組劃分、資料流）
  - ✅ 技術約束（哪些 UI 想法技術上不可行）
  - ✅ 性能要求（API 響應時間、記憶體限制等）
  - ✅ 相容性需求（Illustrator 版本、OS 支援）

**與 Developer 的溝通**
- **何時**：UI&UX 設計完成，開發開始時
- **溝通內容**：
  - 技術方案說明（為什麼選擇 X 而不是 Y？）
  - API 設計文檔（輸入輸出格式）
  - 代碼結構建議（推薦的檔案組織）

**防線機制**
- ⚠️ 如發現開發偏離架構 → 立即觸發 @ARCHITECT_INTERVENTION → 評估影響範圍
- ⚠️ 如發現技術方案不可行 → 與 UI&UX 協商替代方案

**與 QA 的溝通**（如需要）
- **何時**：複雜功能的測試策略規劃
- **溝通內容**：建議的測試方案（自動化 vs 手動、邊界條件識別）

---

### 3️⃣ UI&UX 設計師的溝通

**與 Architect 的溝通**
- **何時**：收到架構報告後
- **確認內容**：
  - 技術約束是什麼？（哪些 UI 想法不可行？）
  - 性能目標是什麼？（響應時間、記憶體）
  - 清晰點：針對不明之處提問

**與 Developer 的溝通**
- **何時**：設計完成後，開發開始前
- **溝通內容**：
  - ✅ UI 原型和互動流程圖
  - ✅ 設計規範文檔（色彩、排版、間距、組件樣式）
  - ✅ 可點擊原型或 HTML 演示
  - ✅ 已知限制和替代方案
- **簽署**：Developer 確認「可以按照此設計實現」

**與 QA 的溝通**（測試階段）
- **何時**：QA 進行手動 UI 測試時
- **溝通內容**：
  - UI 是否符合設計規範？
  - 交互流程是否符合原型？
  - 用戶旅程是否正確實現？

**防線機制**
- ⚠️ 如 Developer 發現設計不可實現 → 立即觸發 @UX_INTERVENTION → 協商調整設計
- ⚠️ 如 QA 發現可用性問題 → 立即觸發 @UX_INTERVENTION → 評估是否需要調整設計

---

### 4️⃣ Developer 的溝通

**與 UI&UX 的溝通**
- **何時**：開發開始時
- **確認內容**：
  - 設計規範清楚嗎？有無疑問？
  - 有無技術無法實現之處？
  - 需要修改設計嗎？

**與 Architect 的溝通**
- **何時**：開發中發現問題時
- **溝通場景**：
  - 發現架構偏差 → 「座標系統設計有誤」
  - 性能瓶頸 → 「100 個物件無法在 2 秒內排版」
  - 技術不可行 → 「該算法無法用 JavaScript 實現」
- **行動**：立即觸發 @ARCHITECT_INTERVENTION

**與 QA 的溝通**
- **何時**：代碼提交後
- **溝通內容**：
  - Code Commit 訊息（清楚說明改動內容）
  - 測試建議（哪些邊界情況需要特別測試？）
  - 已知限制（有無未完成的部分？）

**與其他 Developer 的溝通**
- **何時**：Code Review
- **溝通內容**：
  - 代碼是否符合規範？
  - 是否有可改進之處？
  - 有無性能問題？

---

### 5️⃣ QA 的溝通

**與 Developer 的溝通**
- **何時**：收到代碼後、發現 Bug 時
- **溝通內容**：
  - 測試計畫（計畫測試什麼？）
  - Bug 報告（哪個功能、如何重現、預期 vs 實際）
  - 測試環境確認（Illustrator 版本、OS、測試數據）

**與 Architect 的溝通**
- **何時**：發現架構層面的 Bug 時
- **溝通內容**：「這不是代碼 Bug，而是架構設計問題」

**與 UI&UX 的溝通**
- **何時**：進行手動 UI 測試時
- **確認內容**：
  - UI 是否符合設計規範？
  - 交互流程是否正確？
  - 用戶旅程是否順暢？

**測試報告**
- ✅ 自動化測試報告（成功率、失敗項目）
- ✅ 手動測試報告（測試清單、Bug 清單、簽署）

---

### 6️⃣ DevOps 的溝通

**與 QA 的溝通**
- **何時**：QA 測試通過後
- **確認內容**：
  - 所有 Bug 都修復了嗎？
  - 測試報告已簽署嗎？
  - 可以部署了嗎？

**與 Developer 的溝通**
- **何時**：部署時發現問題
- **溝通場景**：
  - 編譯失敗 → 「需要確認代碼配置」
  - 部署失敗 → 「需要檢查外掛目錄權限」
  - 版本衝突 → 「需要確認版本號遞進規則」

**與 Doc Manager 的溝通**
- **何時**：部署完成後
- **溝通內容**：
  - ✅ 部署完成確認
  - ✅ 新的版本號
  - ✅ git tag 資訊
  - ✅ 變更清單（哪些功能新增、哪些 Bug 修復）

---

### 7️⃣ Doc Manager 的溝通

**與 DevOps 的溝通**
- **何時**：收到部署完成確認後
- **確認內容**：
  - 版本號是什麼？
  - 新增了什麼功能？
  - 修復了什麼 Bug？
  - 有無向下不相容的改動？

**與各角色的溝通**（如文檔遺漏）
- **何時**：發現文檔不完整時
- **溝通對象**：
  - 功能文檔遺漏 → 聯繫 PM / Developer
  - 架構文檔遺漏 → 聯繫 Architect
  - UI 文檔遺漏 → 聯繫 UI&UX 設計師

**文檔清單**
- ✅ README.md（功能說明、快速開始）
- ✅ ARCHITECTURE.md（架構圖、模組說明）
- ✅ CHANGELOG.md（版本記錄、新增功能、Bug 修復）
- ✅ DECISIONS.md（為什麼這樣設計？）
- ✅ DEVELOPMENT_LOG.md（開發進度、已知限制）

---

### 8️⃣ Translator 的溝通

**自動監聽**
- 用戶輸入是否符合 @CODE 格式？
- 用戶是否使用口語化指令？
- 需求是否清晰明確？

**轉化流程**
```
用戶：「這個功能有點問題」
  ↓
Translator 分析：「這涉及架構級問題」
  ↓
Translator：「我認為這是架構級問題，需要 Architect 介入，你同意嗎？」
  ↓
如用戶同意 → 觸發 @ARCHITECT_INTERVENTION
```

## 🚨 防線機制與緊急溝通

### 何時需要「立即溝通」（不走正常流程）

| 情況 | 觸發者 | 通知對象 | 行動 |
|------|--------|--------|------|
| 發現架構偏差 | Developer | Architect | @ARCHITECT_INTERVENTION |
| 發現可用性問題 | QA / UI&UX | UI&UX 設計師 | @UX_INTERVENTION |
| 發現產品方向偏離 | PM / Architect | PM | @PM_INTERVENTION |
| 發現技術不可行 | Developer / Architect | Architect | @ARCHITECT_INTERVENTION |
| 發現 Critical Bug | QA | Developer | @BUG_FIX（優先級 P0） |
| 部署失敗 | DevOps | Developer / Architect | 立即調查 |

**規則**：任何角色發現問題，都可以直接「越級溝通」，但需要在日誌中記錄。

## 💬 常見溝通誤區

### ❌ 誤區 1：「我以為別人知道...」
**問題**：假設溝通，但沒有正式確認  
**解決**：總是顯式確認（口頭 + 文檔）

### ❌ 誤區 2：「我發現問題但沒告訴你...」
**問題**：發現問題但沒有及時上報，導致後期才發現  
**解決**：任何發現都要立即記錄和上報，觸發防線機制

### ❌ 誤區 3：「需求一直在變...」
**問題**：開發中不斷改需求，打亂整個計畫  
**解決**：新需求必須經過 PM 評估和優先級調整，進入下一個 Sprint

### ❌ 誤區 4：「我直接改代碼，不告訴設計師...」
**問題**：Developer 改了設計但沒通知 UI&UX，導致 QA 發現問題  
**解決**：任何設計改動都要 UI&UX 同意

## ✅ 最佳實踐

### ✅ 實踐 1：「每個交接點都有簽署」
每個角色完成工作後，需要下一個角色的「簽署」確認。

### ✅ 實踐 2：「有事立即說，不要拖延」
發現任何問題（技術、設計、需求），立即上報，不要希望後期自動解決。

### ✅ 實踐 3：「文檔優先於口頭」
重要決策和確認都要記錄在文檔中，避免遺忘。

### ✅ 實踐 4：「周期性同步會議」
建議每週進行一次「跨角色同步」，討論進度和問題。

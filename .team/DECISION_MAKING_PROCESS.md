# 決策執行流程 - 開發過程中的行動規範

> **目的**：明確定義在開發過程中，什麼類型的決策需要「先確認再執行」，什麼可以「直接執行」
> **讀者**：所有角色（PM、Architect、UI&UX 設計師、Developer、QA、DevOps、Doc Manager、Translator）
> **原則**：確保重要決策得到授權，同時不減緩開發速度

---

## 📋 決策分類與執行規則

### 級別 1️⃣：「立即執行」- 直接行動，無需確認

**定義**：低風險、易於逆轉、不影響整體方向的決策

| 決策類型 | 具體例子 | 執行方式 | 誰可以執行 |
|---------|---------|---------|-----------|
| **日常代碼修改** | 修復 Bug、重構代碼、優化性能 | 直接執行 → git commit | Developer |
| **文檔更新** | 添加註釋、更新 README、記錄決策 | 直接執行 → git commit | 各角色 |
| **小型 UI 調整** | 改按鈕顏色、調整間距 1-2px、改字體大小 1-2px | 直接執行 → git commit | Developer / UI&UX |
| **代碼審查反饋** | 代碼風格改進、變數命名、邏輯簡化 | 直接執行 → git commit | Developer |
| **測試用例編寫** | 添加新的測試、擴展現有測試 | 直接執行 → git commit | QA |
| **部署流程優化** | 改進編譯步驟、優化部署腳本 | 直接執行 | DevOps |
| **日誌輸出改進** | 添加調試日誌、改進錯誤訊息 | 直接執行 → git commit | Developer |

**執行後的行動**：
- ✅ 直接提交 git commit（語義化訊息）
- ✅ 無需事先報告（但推薦在日報中記錄）
- ✅ 由 Code Review 人員檢查

**例子**：
```
Developer 發現一個拼寫錯誤 → 直接修正 → git commit: "fix: 修正日誌訊息拼寫"
QA 添加新的測試用例 → 直接添加 → git commit: "test: 添加邊界條件測試"
```

### 級別 2️⃣：「先確認再執行」- 需要授權，但流程快速

**定義**：中等風險、影響範圍較大、但可通過正式確認解決

| 決策類型 | 具體例子 | 執行前 | 執行方式 | 誰批准 |
|---------|---------|--------|---------|--------|
| **功能實現選擇** | 「用 Algorithm A 還是 B」「快速排版 vs 精確排版」 | 提出選項 + 分析 → 等批准 | 提交 PR + Architect 審核 | Architect |
| **代碼結構調整** | 「重新組織檔案夾」「改 API 設計」「改數據結構」 | 提出方案 → 等批准 | 直接執行，PR 中解釋 | Architect |
| **第三方庫引入** | 「添加新的 npm 包」「集成外部代碼」 | 提出理由 → 等批准 | 直接執行，更新 package.json | Architect |
| **代碼複用/集成** | 「從資料庫集成現成代碼」 | 提出方案 → 參照 INTEGRATION_CHECKLIST.md | 按檢查清單執行 | Architect / PM |
| **API 端點改動** | 「改 API 參數」「改返回格式」 | 提出改動 → 通知使用方 | 直接執行，但需向 Developer 通知 | Architect |
| **模組介面改動** | 「改函數簽名」「改模組導出」 | 提出改動 → 確認影響範圍 | 直接執行，但需向依賴者通知 | Architect |
| **性能優化決策** | 「用快取」「改算法」「並行處理」 | 提出方案 + 性能數據 → 等批准 | 直接執行，QA 驗證性能 | Architect |
| **錯誤處理策略** | 「如何處理異常」「如何記錄錯誤」 | 提出規範 → 等批准 | 直接執行 | Architect |
| **版本號遞進** | 「Major vs Minor vs Patch」 | 提出理由 → PM 確認 | 直接執行 | PM / DevOps |

**執行前的確認流程**：
```
1. Developer/Architect 提出方案
   ├─ 說明「想做什麼」
   ├─ 說明「為什麼這樣做」
   └─ 說明「影響範圍」
   ↓
2. 等待批准人的反饋（通常 1-2 小時）
   ├─ ✅ 同意 → 直接執行
   ├─ ⚠️ 有疑問 → 討論澄清 → 執行
   └─ ❌ 不同意 → 提出替代方案
   ↓
3. 執行決策
   ├─ 在 PR 或 commit 訊息中詳細說明理由
   └─ 由 Code Review 人員最終驗證
```

**例子**：
```
Developer：「我想改 API 返回格式，從 {result: []} 改成 {data: [], meta: {}}」
Architect：「為什麼？」
Developer：「方便添加 metadata（如分頁信息），這是行業慣例」
Architect：「同意，但需要通知所有使用此 API 的地方」
Developer：「已確認，只有 3 個地方使用，一起更新」
Architect：「✅ 批准」
Developer：直接執行改動 → git commit: "refactor: 改 API 返回格式以支援 metadata"
```

### 級別 3️⃣：「必須先討論再執行」- 需要詳細規劃與批准

**定義**：高風險、影響整體方向、不容易逆轉的決策

| 決策類型 | 具體例子 | 討論方式 | 批准人 | 注意事項 |
|---------|---------|---------|--------|---------|
| **新增/移除功能** | 「新增旋轉支援」「移除某個功能」 | PM 評估 → 提交設計文檔 | PM + Architect | 影響 MVP、時程、工作量 |
| **架構重大改動** | 「重新設計模組結構」「改核心算法」「改數據流」 | Architect 提方案 + 風險評估 | Architect + 技術評審 | 影響整個開發計畫 |
| **技術棧改變** | 「改程式語言」「改前端框架」「改數據庫」 | Architect 詳細分析 + PoC | Architect + PM | 影響招人、學習成本 |
| **UI&UX 重設計** | 「完全改設計風格」「改用戶流程」「改信息架構」 | UI&UX 提設計稿 + 用戶研究 | UI&UX + Architect + Developer | 影響開發工作量和進度 |
| **性能/安全目標改變** | 「從 2 秒改為 500ms」「新增加密」「新增權限管理」 | 提出需求 + 技術評估 | Architect + PM | 影響開發複雜度和時程 |
| **用戶反饋導致的大改動** | 「用戶說功能完全用不了，需要重做」 | PM 評估影響 + 提出改進方案 | PM + Architect | 可能影響其他功能 |
| **技術債決策** | 「為了趕時間，先用快速方案，後續償還」 | Architect 提方案 + 償還計畫 | Architect + PM | 記錄在 DECISIONS.md |
| **跨項目影響** | 「改動會影響其他項目」「需要共享模組」 | 詳細討論 + 協調 | 涉及的所有專案 PM | 需要多方同意 |

**執行前的詳細討論流程**：
```
1. 提出方案（可以是任何角色）
   ├─ 寫成「設計文檔」或「RFC」（3-5 頁）
   ├─ 說明「背景和原因」
   ├─ 說明「幾個可選方案」
   ├─ 說明「推薦方案和理由」
   ├─ 說明「風險評估」
   └─ 說明「工作量和時程影響」
   ↓
2. 安排「設計評審會」（30-60 分鐘）
   ├─ 提案人解釋方案
   ├─ Architect 評估技術可行性
   ├─ PM 評估商業影響
   ├─ Developer 評估工作量
   ├─ 提問和討論
   └─ 記錄決策
   ↓
3. 做出決策
   ├─ ✅ 批准 → 記錄在 DECISIONS.md → 開始執行
   ├─ ⚠️ 有條件批准 → 調整方案 → 重新評審
   └─ ❌ 不批准 → 尋找替代方案
```

**例子**：
```
【RFC】支援 180° 旋轉

背景：用戶反饋某些特殊用途需要 180° 旋轉

可選方案：
1. 只支援 90°/180°/270° 的固定旋轉
2. 支援自由旋轉角度（0°-360°）
3. 只支援 180° 旋轉（最簡化）

推薦：方案 1（固定旋轉）
理由：
- 用戶需求明確（主要是 180°）
- 實現複雜度適中（+3 天）
- 不影響現有功能

風險：
- 需要重新設計座標轉換邏輯（高風險）
- 需要修改邊界計算（高風險）

工作量：5 天（設計 1 天 + 開發 3 天 + 測試 1 天）

決策：在 2026-04-20 的設計評審會上批准
執行人：Developer
開發時間：2026-04-20 到 2026-04-25
```

## 🔄 流程與規則的整合

### 在開發流程中的應用

**PM 角色**
```
【產品規劃階段】
- 級別 3️⃣ 新增功能、改優先級 → 與用戶討論 ✓
- 級別 2️⃣ 資料庫檢索結果 → 快速確認 ✓
- 級別 1️⃣ 記錄決策 → 直接執行 ✓
```

**Architect 角色**
```
【架構設計階段】
- 級別 3️⃣ 技術棧改變、架構重設計 → 詳細評審 ✓
- 級別 2️⃣ 模組介面改動、第三方庫 → 快速確認 ✓
- 級別 1️⃣ 文檔更新 → 直接執行 ✓

【開發監督】
- 級別 3️⃣ 發現技術不可行 → 立即介入 @ARCHITECT_INTERVENTION
- 級別 2️⃣ 發現性能問題 → 建議改進 
- 級別 1️⃣ Code Review → 進行審查
```

**UI&UX 設計師角色**
```
【設計階段】
- 級別 3️⃣ 完全改設計風格 → 詳細評審 ✓
- 級別 2️⃣ 小型 UI 調整、組件改動 → 快速確認 ✓
- 級別 1️⃣ 設計規範記錄 → 直接執行 ✓

【監督】
- 級別 3️⃣ 發現可用性重大問題 → 立即介入 @UX_INTERVENTION
- 級別 2️⃣ 發現設計實現問題 → 與 Developer 討論
```

**Developer 角色**
```
【開發階段】
- 級別 3️⃣ 發現技術不可行 → 立即報告 @ARCHITECT_INTERVENTION
- 級別 2️⃣ 功能實現選擇 → 向 Architect 確認
- 級別 1️⃣ 日常代碼修改 → 直接執行 ✓
```

**QA 角色**
```
【測試階段】
- 級別 3️⃣ 發現需求實現有誤 → 立即報告，可能影響後續
- 級別 2️⃣ Bug 分類和優先級 → 記錄清楚
- 級別 1️⃣ 測試用例編寫 → 直接執行 ✓
```

**DevOps 角色**
```
【部署階段】
- 級別 3️⃣ 發現部署無法進行 → 立即報告，需要回到 Developer
- 級別 2️⃣ 版本號遞進、部署流程 → 向 PM/Architect 確認
- 級別 1️⃣ 部署腳本優化 → 直接執行 ✓
```

## ✅ 執行規則總結

### 原則 1️⃣：「不確定就問，不要假設」
如果不確定某個決策屬於哪個級別，**寧可多問一次，也不要擅自執行高風險決策**。

### 原則 2️⃣：「防線機制優先」
如果在開發過程中發現問題（技術不可行、可用性問題等），**立即觸發防線機制**，不要繼續推進。

### 原則 3️⃣：「文檔優先於口頭**
級別 2️⃣ 以上的決策，都要記錄在文檔中（DECISIONS.md）。

### 原則 4️⃣：「快速反饋」
級別 2️⃣ 的決策，批准人應在 1-2 小時內給出反饋，不要拖延。

### 原則 5️⃣：「事後記錄」
即使是級別 1️⃣ 的決策，也應該在 commit 訊息中清楚說明理由。

## 🚨 防線機制與決策流程的銜接

### 何時觸發防線機制（立即上報，無需等待）

| 觸發情況 | 立即上報給 | 觸發指令 |
|---------|-----------|--------|
| 發現架構偏差 | Architect | @ARCHITECT_INTERVENTION |
| 發現可用性問題 | UI&UX 設計師 | @UX_INTERVENTION |
| 發現產品方向偏離 | PM | @PM_INTERVENTION |
| 發現技術不可行 | Architect | @ARCHITECT_INTERVENTION |
| 發現 Critical Bug | Developer + QA | @BUG_FIX（P0 優先級） |
| 發現進度無法趕上 | PM | @PM_REPRIORITIZE |

**防線機制的優先級 > 決策流程的優先級**  
即使在執行級別 1️⃣ 的任務，如果發現防線機制被觸發，**立即暫停並上報**。

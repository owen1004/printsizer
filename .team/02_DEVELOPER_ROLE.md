# Developer 角色 SOP - 開發工程師

> **職責**：實現功能、編寫代碼、識別技術風險

---

## 何時觸發 Developer 角色？

✅ **必須觸發**
1. 架構設計完成並通過 Architect 審核後（@START_DEVELOPMENT）
2. QA 發現 Bug 並分類後（@BUG_FIX）

✅ **防線機制**
- 發現架構偏差時立即觸發 @ARCHITECT_INTERVENTION
- 發現性能瓶頸或技術不可行時立即上報

---

## Developer 工作流程

```
【輸入】
Architect 審核報告（通過✓）+ UI&UX 設計規範
  ↓
【開發前確認】
  ├─ 與 UI&UX 確認設計無誤（是否有技術無法實現？）
  ├─ 與 Architect 確認架構方向清晰
  └─ 開發環境已準備 ✓
  ↓
【代碼開發】
  ├─ 編寫核心邏輯
  ├─ 識別並記錄技術債（如有）
  ├─ 撰寫程式註釋和文檔
  └─ 進行自我測試
  ↓
【Code Review】
  ├─ 與其他 Developer 進行程式碼審查
  └─ 確認符合規範
  ↓
【代碼提交】
  ├─ git commit（語意化訊息格式）
  ├─ 寫清楚改動內容、測試建議、已知限制
  └─ 提交測試建議給 QA
  ↓
【輸出】
Code 已 Commit ✓ → 自動進入 QA 測試階段
```

## 開發前核查

### 與 UI&UX 的溝通

**觸發時機**：開發開始時

**確認項目**：
- [ ] 設計規範清楚嗎？有無疑問之處？
- [ ] 設計中有無技術無法實現的地方？
- [ ] 是否需要修改設計以適應技術限制？

**行動**：
- 若發現技術無法實現 → 立即與 Architect 討論
- 若設計需要修改 → 與 PM 和 Architect 確認後再調整

### 與 Architect 的溝通

**觸發時機**：開發中發現問題時

**報告場景**：
```
1. 架構偏差
   ├─ 「座標系統設計有誤，無法達到精度要求」
   └─ → 立即觸發 @ARCHITECT_INTERVENTION

2. 性能瓶頸
   ├─ 「100 個物件無法在 2 秒內排版」
   └─ → 可能需要調整演算法或架構

3. 技術不可行
   ├─ 「該演算法無法用 JavaScript 實現」
   └─ → 需要改用其他方案
```

**行動**：
- 描述問題的具體症狀（不是猜測）
- 提供已嘗試的解決方案
- 準備好與 Architect 討論替代方案

## 代碼編寫規範

### 程式碼結構

✅ **要求**：
- 將「計算邏輯」與「DOM 操作」分開
- 邏輯層應該易於測試和驗證
- DOM 層可以手動測試驗證

❌ **避免**：
- 跳過錯誤處理
- 跳過邊界條件檢查
- 完全無文檔無註釋
- 核心模組設計不清楚

### 技術債識別

**在開發中發現的技術債，立即記錄**：

```markdown
【開發中發現的技術債】

Commit: [commit hash] - 功能描述

【技術債 #X】簡短描述
- 代碼位置：[檔案路徑] 第 X-Y 行
- 描述：[具體是什麼問題]
- 如何發現：[在什麼情況下發現]
- 臨時方案：[目前的解決方式]
- 完整方案：[理想解決方式]
- 優先級：🔴 P0（需立即修復）/ 🟡 P1（可延後）/ 🟢 P2（未來考慮）
- 預估工時：[多少天]
```

### 測試編寫

**若開發 .jsx 邏輯**：
- 撰寫單元測試（Layer 1：test_template_unit.jsx）
- 撰寫集成測試（Layer 2：test_template_integration.jsx）
- 測試覆蓋率 > 80%

**測試編寫時機**：
- 核心邏輯完成後立即編寫
- 測試應涵蓋邊界條件（空、零、負數、超大值等）

## Code Review 流程

### 與其他 Developer 的溝通

**觸發時機**：代碼完成、提交前

**審查內容**：
- [ ] 代碼是否符合項目規範？
- [ ] 邏輯是否清晰易懂？
- [ ] 有無效能問題？（迴圈中重複計算、不必要遞歸等）
- [ ] 有無邊界條件遺漏？
- [ ] 錯誤處理是否完整？

**反饋機制**：
- 審查者提出意見
- 開發者修改後再次提交
- 審查者確認無誤後才能 Commit

## Git Commit 與交付

### Commit 訊息格式

**語意化格式**（必須遵守）：

```
feat: 新增座標轉換邏輯
fix: 修復邊距計算錯誤
refactor: 重構排版演算法
docs: 更新函數文檔
test: 添加邊界條件測試
```

**Commit 訊息要求**：
- 第一行簡述改動內容（不超過 50 字）
- 第二行空白
- 後續行提供詳細說明（如需要）
- 若涉及技術債，附註技術債編號

**範例**：
```
feat: 實現 NFP 拼版演算法

- 支援 0°/90°/180°/270° 旋轉
- 邊界檢查已完整實現
- 已知技術債 #1：性能優化待處理（計畫 Sprint 2）

Commit Message 格式遵守語意化規範
```

### 交付給 QA

**提交前清單**：

- [ ] 代碼已 Commit，訊息清晰
- [ ] Code Review 已通過
- [ ] 自我測試已完成
- [ ] 技術債已記錄（如有）

**提交給 QA 的信息**：

```markdown
【開發完成交付】

功能名稱：[功能描述]
Commit ID：[commit hash]

## 測試建議

[哪些邊界情況需要特別測試？]
- 邊際 1：...
- 邊際 2：...

## 已知限制

[有無未完成的部分？有無已知的限制或問題？]
- 限制 1：...
- 限制 2：...

## 技術債

[有無在開發中引入的技術債？]
- 技術債 #1：...（計畫 Sprint X 償還）

## 測試環境

- Illustrator 版本：2026
- 測試資料：[提供測試用的樣本檔案或數據]
```

## Bug 修復流程

### QA 報告 Bug 後

```
QA 報告：Bug #3（Critical）
  ↓
觸發：@BUG_FIX
  ↓
【分析 Bug】
  ├─ 理解重現步驟
  ├─ 確認預期 vs 實際
  └─ 定位代碼位置
  ↓
【修復代碼】
  ├─ 修改相關邏輯
  ├─ 確保不引入新 Bug
  └─ 驗證修復有效
  ↓
【提交修復】
  ├─ git commit -m "fix: 修復 #BugID - 簡短描述"
  ├─ 提供修復說明
  └─ 送回 QA 重新測試
  ↓
QA 確認無誤 → 進入 DevOps（發佈）
```

### Commit 訊息格式

```
fix: 修復 #BugID - 邊距計算錯誤

## 問題
- 當邊距設為 0mm 時，排版邏輯無法正確判斷邊界

## 修復方案
- 在邊界檢查中添加 >= 判斷，替代原有的 >
- 添加測試用例驗證零邊距情況

## 驗證
- 單元測試通過
- 手動測試確認修復有效
```

## Developer 最佳實踐

1. **代碼質量優先**
   - 寧願多花時間確保代碼品質，也不要趕進度犯錯

2. **及時溝通**
   - 發現任何不確定，立即與相關角色討論
   - 不要假設，確認設計後再寫代碼

3. **文檔要清晰**
   - Commit 訊息要讓 6 個月後的自己能看懂
   - 複雜邏輯要有清晰註釋

4. **測試要完整**
   - 邊界條件、異常情況都要測試
   - 不要只測「正常情況」

5. **技術債要記錄**
   - 任何快速實現的地方，立即記錄作為技術債
   - 不能「希望後來會修」，必須有償還計畫

# ✅ 技術債檢查清單

> **用途**：確保在開發過程中識別、評估、記錄和管理技術債，防止債務螺旋
> **使用時機**：在每個開發階段（架構設計、開發、QA）進行檢查
> **讀者**：Architect、Developer、QA

---

## 📋 架構設計階段 - 技術債識別

### 預設計階段檢查

在技術方案設計完成後，Architect 應該檢查：

**模組設計**
- [ ] 模組邊界是否清晰？（易於修改而不影響其他模組）
- [ ] 模組間是否有過度耦合？（改一個模組需要修改多個地方）
- [ ] 是否有「暫時」的設計？（標記出來作為技術債）

**算法選擇**
- [ ] 選擇的算法是否是「最優」還是「夠用」？
  - [ ] 如果是「夠用」，為什麼？（時間限制？複雜度？）
  - [ ] 是否有優化計畫？
- [ ] 算法的邊界條件都考慮了嗎？（不考慮邊界 = 技術債）

**依賴管理**
- [ ] 是否引入了過多的外部依賴？
- [ ] 依賴的庫是否穩定？（風險評估）
- [ ] 有無「過度設計」的風險？（引入不必要的複雜性）

**性能和可擴展性**
- [ ] 現有設計是否滿足性能目標？
- [ ] 有無「快速實現，後續優化」的地方？
- [ ] 數據結構選擇是否適當？（例如：陣列 vs 鏈表 vs 樹）

**錯誤處理**
- [ ] 所有可能的錯誤都有處理嗎？
- [ ] 邊界條件都檢查了嗎？（例如：空陣列、超大數值）
- [ ] 錯誤訊息是否清晰有用？

**記錄格式**：
```markdown
【可能的技術債 - 架構設計階段】

【技術債 1】座標轉換算法
- 現狀：使用快速近似算法（精度 95%）
- 邊界情況：特殊形狀、極端尺寸可能有偏差
- 為什麼接受：精確算法需要 3 天額外開發
- 償還計畫：Sprint 2，當有用戶反饋時優先處理
- 優先級：🟡 P1
- 負責人：[待定]

【技術債 2】暫時的數據序列化
- 現狀：使用簡單的 JSON 序列化
- 問題：不支援複雜的嵌套結構
- 為什麼接受：目前數據結構簡單，夠用
- 償還計畫：當數據結構複雜化時再優化
- 優先級：🟢 P2
- 負責人：[待定]
```

## 💻 開發階段 - 技術債監控

### Developer 應該檢查的項目

**代碼品質**
- [ ] 代碼是否遵循架構規範？（或是「臨時快速實現」）
- [ ] 是否有「TODO」註釋標記臨時代碼？（例如：`// TODO: 優化這個邊界情況`）
- [ ] 代碼複雜度是否過高？（單個函數超過 20 行考慮分割）
- [ ] 是否有重複代碼？（複製粘貼 = 技術債）

**錯誤處理**
- [ ] 所有可能的錯誤都有 try-catch 嗎？
- [ ] 異常訊息是否清晰？（誰會看到這個訊息？能理解嗎？）
- [ ] 邊界條件都檢查了嗎？（不檢查 = 隱藏 Bug）

**性能考慮**
- [ ] 是否有明顯的性能問題？（例如：迴圈中重複計算、無端的遞歸）
- [ ] 是否可以優化？（如果可以，何時優化？）
- [ ] 記憶體使用是否合理？（是否有記憶體洩漏風險）

**文檔和註釋**
- [ ] 複雜邏輯是否有清晰的註釋？
- [ ] 函數簽名是否有文檔？（參數、返回值、可能的異常）
- [ ] 是否記錄了「為什麼這樣做」？（不只是「做了什麼」）

**測試覆蓋**
- [ ] 核心邏輯是否有測試？
- [ ] 邊界條件是否被測試？
- [ ] 是否有已知的「不會測試的情況」？（記錄為技術債）

**記錄格式**：
```markdown
【開發中發現的技術債】

Commit: abc1234 - 實現拼版排列算法

【技術債】邊界情況不完整
- 代碼位置：src/layout/nesting.js 第 120-150 行
- 描述：目前不支援「零面積物件」，會導致排版異常
- 如何發現：編寫測試時發現
- 臨時方案：檢查並過濾零面積物件（簡單但不完美）
- 完整方案：改進邊界檢查邏輯，可能需要 1 天
- 優先級：🔴 P0（需要修復）/ 🟡 P1（可以延後）
- 決策：[接受還是現在修復？]
```

### Architect 的開發監督檢查

**架構偏差檢測**
- [ ] 代碼是否遵循架構設計？
- [ ] 是否有「意外的技術債」（不在原計畫中的）？
- [ ] 有無模組耦合超出預期？

**技術債累積監控**
- [ ] 有多少個新的技術債被識別？
- [ ] 總體技術債是否在控制範圍內？（應該 < 10 項）

**防線觸發**
- [ ] 如果發現「不應該有技術債的地方」有債，是否需要 @ARCHITECT_INTERVENTION？

## 🧪 QA 階段 - 技術債驗證

### 自動化測試檢查

**測試覆蓋**
- [ ] 核心邏輯是否被測試？（覆蓋率 > 80%）
- [ ] 邊界條件是否被測試？
- [ ] 異常情況是否被測試？

**已知技術債的測試**
- [ ] 已接受的技術債是否有「預期失敗」的測試？
  - 例如：「精度 ±2px」的邊界測試

**測試穩定性**
- [ ] 測試是否穩定？（有無間歇性失敗）
- [ ] 有無「測試代碼的技術債」？（例如：重複的測試代碼、複雜的測試邏輯）

### 手動測試檢查

**邊界情況驗證**
- [ ] 極端輸入是否被測試？（空、零、負數、超大值）
- [ ] 特殊情況是否被測試？（重複項、重疊項、衝突項）
- [ ] 已知的技術債是否在「可接受範圍」內？

**性能驗證**
- [ ] 性能是否滿足目標？（例如：< 2 秒）
- [ ] 有無意外的性能問題？（例如：記憶體洩漏、無限迴圈）

**用戶體驗驗證**
- [ ] 錯誤提示是否清晰？
- [ ] UI 是否匹配設計規範？
- [ ] 有無「技術債導致的可用性問題」？

**記錄格式**：
```markdown
【QA 發現的技術債相關問題】

測試項：邊界情況 - 零面積物件

預期：應該被過濾或處理
實際：排版異常，生成了無效結果

相關技術債：#1「邊界情況不完整」
狀態：符合預期（已知技術債，可接受）/ 超出預期（需要立即修復）

如果超出預期：
- 優先級：🔴 P0
- 建議：立即回到 Developer 修復
```

## 📊 技術債清單管理

### 技術債清單模板

在項目根目錄或 `DECISIONS.md` 中維護技術債清單：

```markdown
# 技術債清單

## 主動接受的技術債

### 🔴 P0 - 必須立即償還

| 編號 | 描述 | 現狀 | 計畫償還 | 負責人 | 簽署日期 |
|------|------|------|--------|--------|---------|
| #1 | 座標精度問題 | 進行中 | Sprint 2 | Developer A | 2026-04-20 |

### 🟡 P1 - 應在 2-3 Sprint 內償還

| 編號 | 描述 | 現狀 | 計畫償還 | 負責人 | 簽署日期 |
|------|------|------|--------|--------|---------|
| #2 | 演算法優化 | 待計畫 | Sprint 3 | Developer B | 2026-04-20 |

### 🟢 P2 - 可以延後償還

| 編號 | 描述 | 現狀 | 計畫償還 | 負責人 | 簽署日期 |
|------|------|------|--------|--------|---------|
| #3 | 代碼重構 | 待評估 | TBD | TBD | TBD |

## 已償還的技術債

| 編號 | 描述 | 完成日期 | 驗收人 |
|------|------|---------|--------|
| #0 | 測試框架集成 | 2026-04-15 | Architect A |
```

### 更新頻率

- **每天**：Developer 發現新技術債時，立即記錄
- **每週**：Architect 審查本週新增技術債
- **每個 Sprint 開始**：評估優先級、分配償還任務
- **每個 Sprint 結束**：驗收償還結果

## 🚨 技術債的紅綠燈

### 🟢 綠燈 - 健康狀態

```
✅ 技術債 ≤ 10 項
✅ P0 技術債 ≤ 2 項
✅ 每個 Sprint 償還的 ≥ 新增的
✅ 開發速度穩定
✅ Bug 率在預期範圍
```

### 🟡 黃燈 - 需要關注

```
⚠️ 技術債 11-20 項
⚠️ P0 技術債 3 項
⚠️ 有多個 Sprint 未償還的 P1 債務
⚠️ 開發速度開始下降
⚠️ Bug 率上升

行動：
- Architect 進行一次「技術債評審」
- 優先償還 P0 技術債
- 考慮暫停新功能開發
```

### 🔴 紅燈 - 危急狀態

```
❌ 技術債 > 20 項
❌ P0 技術債 > 3 項
❌ 多個 P1 技術債長期未償還
❌ 開發速度明顯下降
❌ Bug 率大幅上升

行動：立即上報 PM，討論是否需要：
- 暫停所有新功能開發
- 集中 2-3 個 Sprint 償還技術債
- 可能需要重構某個核心模組
```

## ✅ 最佳實踐

### ✅ 實踐 1：「及時識別，不要隱瞞」
發現技術債立即記錄，不要希望「後來會自動修復」。

### ✅ 實踐 2：「區分「接受」和「忽視」」
- **接受**：知道有債，有償還計畫，記錄清楚
- **忽視**：不承認有問題，最後變成大坑

### ✅ 實踐 3：「優先級要清楚」
P0（立即修復）vs P1（計畫內修復）vs P2（未來考慮）

### ✅ 實踐 4：「償還要有紀律」
不能「永遠都在」償還新技術債，要有計畫地償還舊的。

### ✅ 實踐 5：「文檔優於記憶」
所有技術債都要寫進文檔，不依賴某個人的記憶。

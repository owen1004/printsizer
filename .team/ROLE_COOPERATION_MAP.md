## 決策點與把關

### 誰有決策權？

| 決策點 | 決策者 | 重要度 |
|--------|--------|--------|
| 商業方向是否可行 | 01 Senior PM + 14 BD | 🔴 P0 |
| 產品方向是否正確 | 08 PM + 11 UX | 🔴 P0 |
| 技術方案是否可行 | 03 Architect | 🔴 P0 |
| 設計是否符合品牌 | 13 Brand Designer | 🟡 P1 |
| 功能是否通過測試 | 06 QA | 🔴 P0 |
| 代碼品質是否達標 | 05 Developer | 🟡 P1 |

### 決策記錄方式

所有決策記錄在 `.project/DECISIONS.md`：

```markdown
【決策 #N】決策名稱

決策者：[角色名稱]
日期：[日期]
優先級：P0/P1/P2

決策內容：
[具體決策]

為什麼做這個決策：
[商業理由 / 技術理由 / 用戶價值]

替代方案：
- 方案 A：[成本/風險]
- 方案 B：[成本/風險]

影響範圍：
[哪些功能或模組會受影響]

後續跟蹤：
- [ ] 實現完成
- [ ] 驗收簽署
- [ ] 上線運營
```

## 衝突解決

### 設計 vs 技術

```
場景：UI Designer 要求的設計在技術上無法實現

解決步驟：
1. Architect 評估技術可行性
2. UI Designer 和 Architect 討論替代方案
3. PM 評估對用戶體驗的影響
4. 最終決策記錄在 DECISIONS.md
```

### 功能 vs 時間

```
場景：功能列表無法在預期時間內完成

解決步驟：
1. PM 根據優先級排序
2. Architect 評估技術複雜度
3. 考慮 MVP vs 完整版
4. 調整發佈計畫
5. 技術債決策（延後實現）記錄在 DECISIONS.md
```

## 協作最佳實踐

### 1. 清晰的職責邊界

```
✅ 好的做法：
「08 PM 負責產品需求澄清，11 UX 負責信息架構，
兩者在 PRD 評審會議上對齐設計方向」

❌ 避免：
「不清楚誰負責什麼，導致溝通混亂」
```

### 2. 及時的信息交接

```
✅ 好的做法：
「08 PM 完成 PRD → 發送給 11 UX + 03 Architect
同時請他們提出任何設計 / 技術風險」

❌ 避免：
「信息滯後，下一個角色需要花時間重新理解」
```

### 3. 決策記錄

```
✅ 好的做法：
「每個重要決策都記錄在 DECISIONS.md
包括『為什麼這樣做』和『考慮過的替代方案』」

❌ 避免：
「決策在口頭或零散的郵件中，無法追蹤」
```

# 角色觸發條件與狀態轉移 - Role Triggers & State Machine

> **目的**：定義八角色系統的完整觸發邏輯與狀態轉移流程

---

## 開發流程狀態機

```
【初始狀態】
  ↓
【PM 角色】用戶研究與需求分析 (@NEW_FEATURE / @STRATEGY)
  ↓
【Architect 角色】架構設計與審核 (@ARCHITECT_REVIEW / @ARCHITECT_INTERVENTION)
  ↓
【UI&UX 設計師】使用者體驗設計 (@UX_DESIGN)
  ↓
【Developer（開發）】實作代碼 (@START_DEVELOPMENT)
  ↓
【QA 角色】品質驗證 (@QA_TESTING)
  ├─ ✅ 通過 → 【DevOps 角色】
  └─ ❌ 失敗 → 【Bug Fix】→ 重回 QA
  ↓
【DevOps 角色】版本發佈 (@DEVOPS_DEPLOY)
  ↓
【Doc Manager 角色】文檔同步 (@DOC_SYNC)
  ↓
【發佈完成】
```

---

## 八角色觸發條件矩陣

| 角色 | 自動觸發條件 | 手動觸發指令 | 前置狀態 | 後置狀態 |
|------|-----------|-----------|--------|--------|
| **PM** | 新功能提案、功能疑問、進度查詢 | @NEW_FEATURE, @STRATEGY | 無 | 產品規劃報告 + 需求分析報告 ✓ |
| **Architect** | PM 報告完成、設計變動檢測、技術債識別 | @ARCHITECT_REVIEW, @ARCHITECT_INTERVENTION, @TECH_DEBT_DECISION | PM 完成 | 架構審核報告 + 技術債記錄 ✓ |
| **UI&UX 設計師** | Architect 通過 | @UX_DESIGN, @UX_INTERVENTION | Architect 完成 | 用戶旅程 + UI 原型 + 設計規範 ✓ |
| **開發** | UI&UX 通過、Bug 修復 | @START_DEVELOPMENT, @BUG_FIX | UI&UX 完成 | Code Commit ✓ |
| **QA** | Code Commit 完成 | @QA_TESTING | 代碼完成 | 自動化測試 + 手動測試報告 ✓ |
| **DevOps** | QA 通過 | @DEVOPS_DEPLOY | QA 通過 | 部署完成 ✓ |
| **Doc Manager** | DevOps 部署完成 | @DOC_SYNC | DevOps 完成 | 文檔同步 ✓ |
| **Translator** | 非標準化輸入檢測 | (自動) | 任何 | @CODE 指令轉化 |

## 詳細觸發條件

### 1️⃣ PM 角色觸發

**自動觸發**：
- 用戶提問「要做什麼功能？」→ @NEW_FEATURE
- 用戶問「現在進度如何？」 → @STATUS_CHECK
- 用戶提交需求清單 → 分析需求

**手動觸發**：
```
用戶：「我們需要新增排版引擎」
觸發：@NEW_FEATURE
PM 輸出：需求分析報告 → Architect 審核
```

**前置檢查**：
- ✓ 是否已有明確的功能描述？
- ✓ 用戶是否已確認範疇？

**後置條件**：
- ✓ PM 報告已生成
- ✓ 功能清單已列出
- ✓ 預估工時已提供
- → 自動轉移至 Architect

### 2️⃣ PM 角色觸發（擴充 - 產品策略階段）

**自動觸發**（新增）：
- 用戶提出新產品方向或市場機會
- 收到用戶反饋需要評估商業價值

**手動觸發**（新增）：
```
用戶：「我想開發一個新工具來解決 X 問題」
觸發：@STRATEGY
PM 輸出：產品規劃報告（JTBD、Persona、市場分析）
```

**防線機制**（新增）：
```
如果發現功能方向與產品願景偏離：
觸發：@PM_INTERVENTION
PM：評估影響 → 確認是否繼續
```

**前置檢查**（新增）：
- ✓ 用戶背景和市場機會是否清晰？
- ✓ 相關 Persona 是否已識別？

**後置條件**（新增）：
- ✓ JTBD 分析已完成
- ✓ 用戶 Persona 已構建
- ✓ 市場競品已分析
- ✓ 產品願景已定義
- → 進入需求澄清階段

### 3️⃣ Architect 角色觸發

**自動觸發**：
- PM 報告生成完成
- 開發中發現架構偏差
- 用戶提出「這個改動會影響整體設計嗎？」

**手動觸發**：
```
用戶：「這個改動會不會有問題？」
觸發：@ARCHITECT_INTERVENTION
Architect 輸出：風險評估 + 替代方案
```

**防線機制**（開發中自動觸發）：
```
開發者：「發現座標系統需要重新設計」
自動觸發：@ARCHITECT_INTERVENTION
Architect：評估影響範圍 → 決策是否繼續
```

**前置檢查**：
- ✓ PM 分析報告已完成
- ✓ 技術方案是否已提出

**後置條件**：
- ✓ 架構設計已確定
- ✓ 風險已評估
- ✓ 決策已記錄
- → 自動轉移至開發

### 3️⃣ Architect 角色觸發（擴充 - 技術債管理）← 🆕 新增

**自動觸發**（技術債監控）：
- 開發者提出快速實現方案要求時（需要接受技術債）
- QA 報告發現已知限制且超出預期
- 每個 Sprint 開始前進行技術債評估

**手動觸發**（技術債決策）：
```
用戶/開發者：「先用快速算法上線，後續優化」
觸發：@TECH_DEBT_DECISION
Architect 輸出：技術債決策記錄（可接受/不可接受 + 償還計畫）
```

**技術債識別流程**：
```
【架構設計階段】
Architect 應提出問題：
- ✓ 這個模組有無過度簡化？
- ✓ 這個設計有無隱藏假設？
- ✓ 這個實現有無優化空間？
- 記錄在 DECISIONS.md 中

【開發階段】
Developer 自動識別技術債：
- 代碼複雜度過高
- 跳過邊界條件處理
- 性能優化空間
- 立即記錄 TODO 與優先級

Architect 定期審查：
- 週期性檢查是否有「不應該有技術債的地方」出現了技術債
- 評估技術債累積是否失控（> 10 項時預警）
```

**技術債決策決定流程**：
```
【必須現在修復】（❌ 不能接受技術債）：
- 錯誤處理邏輯
- 邊界條件檢查
- 核心模組設計
- 安全相關代碼
→ 拒絕快速實現，要求完整實現

【可以接受技術債】（✅ 條件式接受）：
- 優化類技術債（算法優化、性能微調）
- 功能擴展類（先支援 3 種，後擴展到 10 種）
- 測試覆蓋類（先手動測試，後自動化測試）
→ 要求：明確償還計畫 + 優先級 + 負責人
```

**技術債償還監控**：
```
【每個 Sprint 開始】
Architect 檢查：
- 有多少個待償還技術債？
- 本 Sprint 要償還哪些？（優先 P0 技術債）
- 有無新的技術債出現？

【每個 Sprint 結束】
Architect 驗收：
- 是否償還了計畫內的技術債？
- 新產生的技術債數量
- 是否需要調整償還計畫？

【技術債健康指標】
🟢 綠燈：
  - 技術債 ≤ 10 項
  - P0 技術債 ≤ 2 項
  - 每 Sprint 償還 ≥ 新增

🟡 黃燈：
  - 技術債 11-20 項
  - P0 技術債 3 項
  - 開發速度下降
  → 觸發 @ARCHITECT_INTERVENTION（評審會）

🔴 紅燈：
  - 技術債 > 20 項
  - P0 技術債 > 3 項
  - Bug 率上升、開發速度明顯下降
  → 上報 PM，討論是否暫停新功能集中償還
```

**前置檢查**（技術債決策）：
- ✓ 快速實現方案已明確
- ✓ 完整實現需要的工作量已評估
- ✓ 業務優先級已確認

**後置條件**（技術債決策）：
- ✓ 技術債決策已記錄在 DECISIONS.md
- ✓ 償還計畫已分配（優先級、時機、負責人）
- ✓ 所有相關人員已確認
- → 繼續開發或進入 Sprint 計畫

**🆕 自動化技術債健康檢查機制**：

```
【自動觸發時機】
✅ Sprint 計畫會議前（自動檢查上個 Sprint 的結果）
✅ Sprint 回顧會議時（生成本 Sprint 的健康指標）
✅ 開發者提交代碼時（檢查是否引入未預期的技術債）
✅ QA 發現 Bug 時（檢查是否與已知技術債相關）

【自動檢查清單】
Architect 應執行以下檢查（可由工具自動化）：

① 技術債計數
  □ 從 DECISIONS.md 統計：
    - 待償還技術債總數
    - P0 / P1 / P2 技術債分佈
    - 預計償還時機已過期的技術債數
  □ 新增未紀錄的技術債（從 git commit 訊息或代碼評審標記）
  
② 健康指標計算
  □ 與上個 Sprint 對比：
    - 技術債新增數 vs 償還數
    - P0 技術債是否按時償還
    - 開發速度是否受影響
  □ 與歷史趨勢對比：
    - 技術債累積是否加速
    - 償還進度是否滯後
    
③ 自動告警條件
  □ 若 技術債 ≥ 11 項 → 黃燈警告
  □ 若 技術債 > 20 項 → 紅燈告警 + 自動 @ARCHITECT_INTERVENTION
  □ 若 P0 技術債 ≥ 3 項 → 紅燈告警
  □ 若 預計償還日期已過但未完成 → 延期警告

【自動輸出】
① 技術債健康報告（Sprint 開始 + 結束時自動生成）
```markdown
【技術債健康檢查報告】
日期：[日期]
Sprint：[Sprint 號]

📊 健康狀況：[🟢 / 🟡 / 🔴]

技術債統計：
- 總數：[N] 項
- P0：[N] 項  P1：[N] 項  P2：[N] 項
- 新增：[N] 項  償還：[N] 項  淨變化：[+/-N] 項

健康指標：
✅ 技術債 ≤ 10 項？[是/否]
✅ P0 技術債 ≤ 2 項？[是/否]
✅ 償還進度達成率？[百分比]
✅ 預期償還已完成？[N/M 項]

預警信息：
[若有黃燈/紅燈，列舉具體項目]

建議行動：
- [對於黃燈的建議]
- [對於紅燈的建議]
```
```

② 自動分派通知
  - 🟡 黃燈 → 通知 Architect，建議召開評審會
  - 🔴 紅燈 → 觸發 @ARCHITECT_INTERVENTION，自動通知 Architect 和 PM

【實現建議】
- 在 `DECISIONS.md` 中保持結構化的技術債列表（便於工具解析）
- 在 git commit 訊息中標記技術債（如 `#TECH_DEBT-1: ...`）
- 可集成 GitHub Actions / GitLab CI 定期執行自動檢查
- 生成的健康報告存檔至 `.project/TECH_DEBT_REPORTS/` 資料夾
```

### 6️⃣ QA 角色觸發

**自動觸發**：
- 代碼 Commit 完成（監聽 git log）
- 收到 DevOps 部署前確認

**手動觸發**：
```
用戶：「開始測試」
觸發：@QA_TESTING
QA：生成測試計畫 → 執行自動化測試 → 執行手動測試 → 產出報告
```

**🆕 測試執行流程（含自動化 .jsx 測試）**：
```
【Step 1】確認是否需要自動化測試
├─ .jsx 腳本？ → 執行 test_runner.jsx
│  ├─ 運行所有單元測試 + 集成測試
│  ├─ 確認 100% 通過
│  └─ 存檔自動化測試報告
├─ C++ 外掛？ → 執行 TestLab
└─ 純 UI？ → 跳過，進入手動測試

【Step 2】執行手動 UI 測試
├─ .jsx 腳本：按 UI_Test_Checklist.md 執行
├─ C++ 外掛：按既有人工測試程序
└─ 記錄所有 Bug

【Step 3】產出測試報告
```

**測試結果決策**：
```
自動化全通過 ✅ + 手動全通過 ✅ → 進入 DevOps
自動化失敗 ❌ 或 手動失敗 ❌ → Bug 清單 → @BUG_FIX → 重回 QA
條件通過 ⚠️ → Critical bug 修復後重新測試
```

**前置檢查**：
- ✓ Code 已完成並 Commit
- ✓ 測試環境已準備
- ✓ 若為 .jsx：ExtendScript Toolkit 已安裝
- ✓ 測試檔案已存在（testlab/jsx_tests/）

**後置條件**：
- ✓ 自動化測試報告已生成（如適用）
- ✓ 手動測試報告已簽署
- ✓ 所有 Bug 已分類並記錄
- ✅ 全通過時 → 轉移至 DevOps
- ❌ 有失敗時 → 轉移至 Bug Fix

**參考資源**：
- 測試指南：`.guidelines/Testing_Guide.md`
- 執行步驟：`.guidelines/Testing_Execution_Steps.md`
- .jsx 測試：`testlab/jsx_tests/README.md`

### 7️⃣ DevOps 角色觸發

**自動觸發**：

**🆕 編譯/部署失敗流程**：
```
【編譯失敗】
DevOps 檢測編譯錯誤
  ↓
分類原因：
├─ 代碼問題 → 觸發 @BUG_FIX（回到 Developer）
├─ 配置問題 → 檢查環境設置 → 重試
└─ 依賴問題 → 更新依賴 → 重試

【部署失敗】
DevOps 檢測部署錯誤
  ↓
分類原因：
├─ 權限問題 → 檢查外掛目錄權限
├─ 版本衝突 → 確認版本號規則
└─ AIP 損壞 → 回到 Developer 重新編譯
```

**版本號遞進**：
- 新功能 → Minor 版本
- Bug 修復 → Patch 版本
- 架構改變 → Major 版本

**前置檢查**：
- ✓ QA 測試通過
- ✓ Illustrator 已關閉
- ✓ 外掛目錄可寫

**後置條件**：
- ✓ 編譯成功
- ✓ AIP 檔案已部署
- ✓ 版本號已更新
- ✓ git tag 已創建
- → 自動轉移至 Doc Manager

### 🚨 **HOTFIX - 緊急修復快速通道**（新增）

**觸發條件**：
- 生產環境發現 Critical Bug
- 無法等待完整測試流程（@QA_TESTING）

**流程**：
```
【發現生產 Critical Bug】
  ↓
【快速診斷】
Dev + Architect：識別根本原因（< 30 分鐘）
  ↓
【快速修復】
Dev：修復代碼（跳過 Code Review）
  ↓
【簡化測試】
QA：只測試修復的功能（跳過完整測試套件）
  ↓
【緊急部署】
DevOps：直接部署（跳過 Doc Manager）
  ↓
【事後補償】
├─ 完整 Code Review（下一個工作日）
├─ 完整測試（下一個工作日）
├─ 文檔更新（下一個工作日）
└─ Hotfix 複盤會議（審視為何進入生產）
```

**條件限制**：
- ⚠️ 只限 Critical（P0）Bug
- ⚠️ 需 Architect 和 DevOps 確認
- ⚠️ 必須在 24 小時內完成事後補償
- ⚠️ 超過 3 次 Hotfix / Sprint → 触發 @PM_INTERVENTION

**風險**：
- 可能引入新 Bug（快速修復的代價）
- 必須記錄為「事後」的完整流程

### 9️⃣ Translator 角色觸發

**自動觸發**（持續監聽）：
- 用戶輸入不符 @CODE 格式
- 用戶使用口語化指令
- 用戶提出模糊需求

**不需觸發**：
- 用戶已發送 @CODE 指令
- 直接調用對應角色

**轉化流程**：
```
用戶：「這個功能有點問題」
↓
Translator 分析：「這是架構級問題」
↓
轉化：@ARCHITECT_INTERVENTION
↓
用戶確認：「是的」
↓
調用：Architect 角色
```

## 🆕 需求全部重做的重置流程（G-10）

> 當用戶說「全部重做」「從頭來」「這個方向不對，換一個」，觸發 @RESET 流程。

### 觸發條件

```
用戶說：
  - 「全部重做」「從頭開始」「這個方向不對」
  - 「之前的代碼都不要了」
  - 「重新規劃」
```

### @RESET 標準動作（Claude 自動執行）

```
【Step 1】確認重置範圍（先問清楚）
  Architect：「您說的重做，是指哪個範圍？
    A. 只是換個實現方法（保留需求方向）
    B. 需求方向也改了（從 PM 階段重來）
    C. 完全清空，連需求都重新定義
    請確認後我再繼續。」

【Step 2】保留有價值的內容（不全盤丟棄）
  檢查以下項目，確認「留」或「丟」：
  ├─ 現有代碼：是否有可複用的函數或模組？
  ├─ 測試用例：是否仍然適用？
  ├─ DECISIONS.md 的決策記錄：標記為「已廢棄」而非刪除
  └─ 架構洞察：踩過的坑，記錄下來避免重蹈

【Step 3】建立重置記錄
  在 DECISIONS.md 新增一條：
  「[日期] @RESET：[原方向] 廢棄原因：[用戶說明的理由]
   保留內容：[列表]  廢棄內容：[列表]」

【Step 4】切換到正確的起點角色
  - 範圍 A → 切換到 Architect 角色重新設計
  - 範圍 B → 切換到 PM 角色重新分析需求
  - 範圍 C → 切換到 Translator，引導用戶重新描述
```

### 重置後的防護

重置後第一個任務開始前，Translator 自動確認：

```
「確認重置完成。新方向摘要：[用戶說明的新方向]
 我們從 [起點角色] 開始。
 
 提醒：上次的教訓是 [從 DECISIONS.md 廢棄記錄中提取]，
 這次我們會注意避免。」
```

## 並行與阻斷規則

**可以並行**：
- PM 與 Architect 可在多個功能上並行（不同特性）
- 開發與 QA 可並行（不同版本）
- 多個開發者可同時開發不同模組（無依賴關係）

**必須阻斷**：
- UI&UX 必須等 Architect 通過
- 開發必須等 UI&UX 通過
- DevOps 必須等 QA 通過
- Doc Manager 必須等 DevOps 完成
- Bug Fix 必須在 QA 失敗後才能啟動
- 🆕 **技術債決策必須在開發前完成**（Architect 評估階段）
- 🆕 **新功能開發必須等技術債決策確認**（防止不受控的技術債積累）

**防線機制**：
- PM 隨時可中斷需求（發現產品方向偏離）
- UI&UX 隨時可中斷開發（發現可用性問題）
- Architect 隨時可中斷開發（發現架構偏差或技術債失控）← **擴充**
- QA 隨時可拒絕部署（Critical Bug）
- 🆕 **Architect 定期評估技術債健康狀況**
  - 🟡 黃燈（11-20 項）：觸發評審會，評估是否暫停新功能
  - 🔴 紅燈（> 20 項）：上報 PM，討論是否集中償還 Sprint
